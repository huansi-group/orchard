# 02 需求分析：面向中小企业的轻量 DataAgent

> 文档版本：v1.0（2026-11-04）  
> 上游输入：GitHub Issue #4《整理业内DataAgent主流功能》  
> 下游文档：[03 功能设计](03-functional-design.md)、[04 分期实施方案](04-phased-delivery.md)

## 1. 背景与问题定义

中小企业做数据分析的典型矛盾是：**业务问题很多、数据人员很少、数据又分散在多个系统与 Excel 中**。常见现象：

- 业务要看一个数，需要提需求、排队、等报表，周期以天/周计；
- 同一个“销售额”在财务、销售、电商三个口径下不一致；
- 数据人员把大量时间花在重复取数与解释口径上；
- 想用大模型问数，但担心答错、越权、数据泄露、SQL 不可追溯；
- 买大型数据平台成本高、实施重，业务迟迟用不上。

本项目的目标不是建设完整数据中台，而是建设一个**轻量、可信、可审计、能持续变准**的 DataAgent 工作台，让业务人员用自然语言完成日常取数、对比、追问与解释，让数据管理员用最低成本维护元数据、语义与权限。

## 2. 产品目标与成功标准

### 2.1 产品目标

1. **业务自助**：业务人员不写 SQL，也能在 3 分钟内得到一个可解释的答案。
2. **回答可信**：答案必须带口径、数据来源、SQL 与新鲜度；核心指标来自统一语义层。
3. **安全可控**：所有查询经过权限校验与 SQL 网关，所有 SQL 可审计，敏感数据可脱敏。
4. **数据闭环**：接入、标注、语义、血缘、问答、审计、反馈形成闭环，系统能越用越准。
5. **轻量可落地**：模块化单体、按需物化、分阶段上线，不强制建仓、不强制上重型调度。

### 2.2 成功标准（试点 3 个月）

| 维度 | 指标 | 目标 |
| --- | --- | --- |
| 业务价值 | 重复取数/报表需求下降 | ≥ 40% |
| 业务价值 | 从提问到获得答案的中位时间 | ≤ 10 分钟 |
| 采纳 | 试点用户周活跃率 | ≥ 60% |
| 质量 | 评测集答案正确率（二期） | ≥ 85% |
| 质量 | SQL 执行成功率 | ≥ 95% |
| 安全 | 越权访问事件 | 0 |
| 安全 | SQL 审计覆盖率 | 100% |
| 体验 | 简单问题 P95 端到端时延 | ≤ 15 秒 |
| 体验 | 用户满意度（5 分制） | ≥ 4.0 |
| 数据 | 核心表标注覆盖率 | ≥ 80% |
| 数据 | 核心链路血缘覆盖率（二期） | ≥ 80% |

> 指标口径：以试点部门真实问题为准；评测集与统计方式见 [04 分期实施方案](04-phased-delivery.md) 第 9 节。

## 3. 用户角色与权限边界（目标态）

| 角色 | 典型人员 | 核心诉求 | 默认权限 |
| --- | --- | --- | --- |
| 业务用户（Viewer） | 销售、运营、财务、门店店长 | 快速查数、看趋势、导出结果 | 使用被授权的智能体与数据集；只读；不可见敏感字段 |
| 分析师（Analyst） | 业务分析、经营分析 | 多轮追问、对比、归因、保存/分享分析 | 业务用户权限 + 创建会话/图表/分享 + 使用探索模式 |
| 数据管理员（Data Admin） | 数据开发、BI 工程师、IT | 接入数据、维护元数据/语义/血缘、处理坏例 | 数据源/数据集/元数据/语义/质量/血缘管理 |
| 平台管理员（Admin） | IT 负责人、系统管理员 | 用户、角色、权限、审计、模型与成本 | 全部平台管理权限；不可绕过审计 |
| 安全/审计（Auditor） | 安全、内控、合规 | 查谁在何时查了什么数据 | 只读审计与报表；不可修改数据 |

**权限原则**：默认拒绝；最小权限；职责分离（数据管理员不能删除审计日志）；智能体权限不得超过使用者权限；敏感操作需二次确认。

## 4. 典型使用场景

### S1 新客户接入与首次问数（P0）

1. 数据管理员添加 MySQL 只读连接，测试通过后系统自动导入 30 张表。
2. 系统识别表/字段注释、主外键与样例数据，生成待标注列表。
3. 管理员为“订单表”“客户表”“商品表”补充业务名、同义词、敏感级别，并发布。
4. 管理员定义“销售额”“订单数”“客单价”三个指标，绑定数据集。
5. 业务用户打开“销售分析助手”，问“上个月华东区销售额是多少？”，系统给出数值、趋势图、口径与 SQL。
6. 用户追问“按品类拆开”，系统继承时间与区域条件，返回品类排名。
7. 管理员在审计页看到本次 SQL、执行人、耗时与结果行数。

**闭环点**：接入 → 元数据 → 标注 → 语义 → 问答 → 审计。

### S2 指标口径争议（P0）

1. 财务与销售对“销售额”口径不一致。
2. 数据管理员在指标页看到两个同名指标，合并为一个受认证指标，写清公式、包含/排除项、负责人。
3. 历史会话中的旧口径答案标记“口径已更新”，新问题强制使用认证指标。
4. （二期）指标变更记录版本与影响范围，通知相关报表/智能体负责人，并纳入回归评测。

**闭环点**：指标治理 → 版本 → 影响分析 → 通知 → 回归评测。

### S3 业务多轮追问与对比（P0）

1. 用户问“本月销售额为什么下降？”
2. 系统先给出总体趋势，再澄清“想看区域、品类还是渠道？”
3. 用户选择“按区域”，系统返回区域贡献度，并指出下降最大的两个区域。
4. 用户追问“和上月比呢？”，系统切换对比口径，保留区域维度。
5. （二期）用户导出图表与明细，分享给主管（只读链接，权限随接收人收敛）。

**闭环点**：多轮上下文 → 分析 → 解释 → 分享 → 反馈。

### S4 敏感数据访问（P1）

1. 业务用户提问涉及客户手机号。
2. 系统识别该字段为 L3 敏感，默认脱敏展示；用户申请查看明文。
3. 数据管理员审批，授予 7 天临时权限；到期自动回收。
4. 所有查看行为写入审计，导出需二次审批。

**闭环点**：敏感识别 → 脱敏 → 申请 → 审批 → 临时授权 → 审计 → 回收。

### S5 SQL 审计与风险复盘（P1）

1. 安全员按“高风险 + 最近 7 天”筛选审计记录。
2. 发现某用户连续执行全表扫描，查看 SQL、执行计划、结果行数与耗时。
3. 系统标记风险原因（无分区/无时间过滤/大表全扫），通知管理员。
4. 管理员优化数据集分区字段或增加行级策略，并在评测集回归。

**闭环点**：审计 → 风险识别 → 策略优化 → 回归。

### S6 答错后的修复闭环（P1）

1. 用户对答案点踩，选择“口径不对”，补充期望结果。
2. 系统生成坏例，自动归类到“指标口径”并指派给数据管理员。
3. 管理员修正指标定义或补充已验证查询，重新验证。
4. 坏例进入回归集，修复后关闭；同类问题准确率提升。

**闭环点**：反馈 → 坏例 → 修复 → 验证 → 回归 → 关闭。

### S7 数据源变更影响分析（P2）

1. 源系统订单表新增字段/修改类型。
2. 系统重新扫描 Schema，识别变更并对比历史元数据。
3. 血缘图列出受影响的数据集、指标、智能体、报表与负责人。
4. 管理员确认影响，更新语义模型并触发回归评测。

**闭环点**：Schema 变更 → 血缘 → 影响分析 → 修复 → 回归。

## 5. 功能需求

优先级：P0 首期必须、P1 二期、P2 后续。期次与 [04 分期实施方案](04-phased-delivery.md) 一致。

### 5.1 数据接入（DS）

| ID | 需求 | 优先级 | 期次 | 验收要点 |
| --- | --- | --- | --- | --- |
| DS-01 | 支持 MySQL、PostgreSQL、CSV/XLSX 数据源接入；后续扩展 SQL Server、Oracle、ClickHouse、Doris、API | P0 | 1 | 连接成功；凭据加密存储；密码不回显 |
| DS-02 | 连接测试与只读账号校验；禁止使用高权限账号 | P0 | 1 | 非只读账号给出明确警告/拒绝；超时与错误可读 |
| DS-03 | 自动导入 Schema：库、表、字段、类型、主外键、注释、行数、样例数据 | P0 | 1 | 导入 100 张表 < 3 分钟；样例数据脱敏 |
| DS-04 | 数据源/数据集浏览、搜索、收藏；显示负责人、更新时间、新鲜度 | P0 | 1 | 关键词搜索 P95 < 500ms；空状态有引导 |
| DS-05 | 同步任务：手动/定时全量、简单增量（时间戳/自增 ID）、字段映射、失败重试 | P1 | 2 | 任务可重跑；失败告警；运行历史可查 |

### 5.2 轻量 ETL 与数据质量（ETL）

| ID | 需求 | 优先级 | 期次 | 验收要点 |
| --- | --- | --- | --- | --- |
| ETL-01 | 基于 SQL 的转换与物化：选择源表、写 SELECT、预览、保存为数据集 | P1 | 2 | 预览 100 行；物化结果可查询；失败可回滚 |
| ETL-02 | 常用转换：字段映射、类型转换、过滤、去重、派生字段、简单 Join | P1 | 2 | 配置化完成，不要求写完整 SQL |
| ETL-03 | 线性任务编排：源表 → 转换 → 目标数据集；支持单依赖与手动触发 | P1 | 2 | DAG 可视化；依赖失败阻断下游 |
| ETL-04 | 调度与运维：Cron、超时、重试、失败告警、运行日志 | P1 | 2 | 支持每日/每小时；失败 5 分钟内告警 |
| ETL-05 | 数据质量规则：非空、唯一、范围、枚举、行数波动、新鲜度；质量结果留存 | P1 | 2 | 规则可启停；失败标记数据集“不可信” |
| ETL-06 | 质量结果进入资产卡片与问答提示；认证数据集必须通过质量门槛 | P1 | 2 | 问答展示“数据质量/新鲜度”提示 |

### 5.3 元数据与标注（META）

| ID | 需求 | 优先级 | 期次 | 验收要点 |
| --- | --- | --- | --- | --- |
| META-01 | 表/字段业务标注：业务名、描述、同义词、单位、枚举含义 | P0 | 1 | 支持批量编辑；保存即生效于检索与问答 |
| META-02 | 标签与业务域：主题域、标签、敏感级别（L1–L4）、负责人 | P0 | 1 | 敏感级别驱动脱敏与权限默认值 |
| META-03 | 业务术语表：术语、定义、同义词、关联字段/指标、负责人 | P1 | 2 | 术语可被问答引用；重复术语有冲突提示 |
| META-04 | 标注工作流：待标注 → 标注中 → 待审核 → 已发布；支持驳回 | P1 | 2 | 状态可追踪；审核记录留痕 |
| META-05 | 资产认证：完整性、质量、新鲜度、使用热度综合评分；认证标识 | P1 | 2 | 认证资产在问答中优先；低分资产提示风险 |
| META-06 | 元数据检索：关键词 + 同义词/术语匹配；按表/字段/指标/术语过滤 | P0 | 1 | Top 10 命中相关；支持“为什么推荐” |

### 5.9 反馈、评估与运营（EVAL / OPS）

## 7. 数据与合规要求

### 7.1 数据分级

| 级别 | 示例 | 默认策略 |
| --- | --- | --- |
| L1 公开 | 产品目录、公开价格 | 登录可见 |
| L2 内部 | 订单明细、库存 | 按数据集授权；导出需权限 |
| L3 敏感 | 客户手机号、地址、身份证号 | 默认脱敏；明文需审批；导出二次审批 |
| L4 高敏 | 银行账号、薪酬、健康信息 | 默认隐藏；仅特定角色可见；全程审计 |

### 7.2 合规要点

- **最小必要**：只采集完成分析所需字段；样例数据默认脱敏。
- **目的限制**：数据仅用于企业内部分析，不用于训练第三方模型（除非明确授权）。
- **可追溯**：谁在何时、通过哪个智能体、执行了什么 SQL、看到了什么结果，均可查。
- **可删除**：支持按用户/数据集删除会话与结果；审计日志按保留期归档。
- **跨境**：支持指定模型/存储区域；默认数据不出部署边界。
- **提示注入**：表注释、业务文档、查询结果中的文本不得作为系统指令执行。

## 8. 范围边界

### 8.1 本期范围（P0/P1）

- 数据接入：MySQL、PostgreSQL、CSV/XLSX。
- 元数据：自动导入、表/字段标注、标签、敏感级别、术语表、检索。
- 语义：数据集、维度、度量、指标、语义编译、已验证查询。
- 血缘：表级/字段级、图谱、影响分析。
- 会话：会话管理、意图/澄清、元数据问答、数据查询、多轮、图表、解读、SQL 展示、反馈。
- 治理：RBAC、列级脱敏、行级权限、SQL 网关、SQL/操作审计、访问审批。
- 运营：质量看板、坏例闭环、评测集、回归、告警、成本。
- 轻量 ETL：SQL 转换、物化、线性调度、质量规则。

### 8.2 明确不做（本期）

- 自研大模型/训练平台；
- 完整数据仓库/湖仓、实时流计算、CDC；
- 复杂 DAG 调度、跨集群计算；
- 主数据管理、MDM、全面数据治理平台；
- 机器学习建模、AutoML；
- 原生 iOS/Android App；
- 数据交易/数据要素流通；
- 多智能体自主协同（仅保留单智能体 + 工具）。

### 8.3 后续可扩展

更多数据源、SSO/LDAP、多租户 SaaS、定时报告、IM 集成、嵌入/API、归因/预测、数据开发 Agent。

## 9. 假设与约束

1. 试点企业规模：10–200 人，1–5 个数据源，50–500 张核心表，10–100 个用户，单表 1 万–100 万行。
2. 数据源可提供只读账号；网络可达；允许在部署边界内处理数据。
3. 大模型通过 API 或私有化部署提供；首期允许使用公有云模型，但需脱敏与合同约束。
4. 现有系统为 Spring Boot + Vue 前后端分离，可在此基础上扩展，不推翻重来。
5. 首期团队 4–6 人，周期按 [04 分期实施方案](04-phased-delivery.md) 估算。
6. 业务方需指定试点部门、数据管理员与指标负责人，否则语义与标注无法闭环。

## 11. 需求优先级与裁剪规则

- **P0 不可裁**：没有它就无法安全地回答一个真实业务问题（连接、元数据、语义、会话、审计、权限）。
- **P1 可延后**：影响闭环质量与规模化，但不阻塞首期试点（ETL、血缘、行级权限、评测）。
- **P2 可替换**：可用人工流程或第三方工具替代（归因、预测、IM、多租户）。
- **裁剪顺序**：先裁 P2，再裁 P1 中的“高级分析/多源/多租户”，不裁 P0 中的“审计/权限/语义”。
- **变更控制**：新增 P0 需求必须说明对首期周期、数据安全与验收指标的影响，由产品与数据负责人共同确认。
